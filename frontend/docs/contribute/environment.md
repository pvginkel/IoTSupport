# Environment Reference

This document captures the ports, environment variables, and configuration files the frontend uses during development and automated testing. Keep it close at hand when wiring up local services or debugging a Playwright run.

## Ports

| Port | Service |
| --- | --- |
| `3100` | The Vite dev server (`pnpm dev`, the dev stack's frontend) and `pnpm preview`. The dev server sets `strictPort`, so a busy port fails the start instead of moving to the next one. |
| `3101` | The dev stack's backend (`Procfile.dev` starts it with `PORT=3101`); it serves the API and the SSE stream. `BACKEND_URL` and `pnpm generate:api` default to it. |
| free ports | Each Playwright worker's own backend and frontend, picked with `get-port` and bound to `127.0.0.1`, so a running dev stack does not collide with the suite. |

## Core Variables

| Variable | Default | Description |
| --- | --- | --- |
| `BACKEND_URL` | `http://localhost:3101` | Read by `vite.config.ts`: the target of the dev and preview servers' `/api` and `/api/sse` proxy rules. Each Playwright worker passes its own backend's URL to its frontend. |
| `VITE_TEST_MODE` | `false` | Read by `vite.config.ts`, which fixes it into the app through `define`; `true` turns on [test mode](#test-mode). `scripts/testing-server.sh` sets it to `true`, and so do the Playwright workers. |
| `PORT` | `3101` | The backend port `pnpm generate:api` fetches the OpenAPI spec from (`scripts/fetch-openapi.js`). `scripts/regenerate-openapi.py` sets it to the backend it starts. |

The Playwright suite reads its own variables—`PLAYWRIGHT_BACKEND_LOG_STREAM`, `PLAYWRIGHT_FRONTEND_LOG_STREAM`, `PLAYWRIGHT_PREVIEW_MODE`, `PLAYWRIGHT_RETAIN_VIDEO`, `INCLUDE_SLOW_TESTS`, `TEST_DATABASE_ADMIN_URL` and `BACKEND_ROOT`; [CI & Execution → Environment Overrides](./testing/ci_and_execution.md#environment-overrides) describes each. The worker fixture sets `BACKEND_URL` and `FRONTEND_URL` in its own process to its services' URLs for the worker's lifetime; the service URLs are the fixtures' to manage, not yours to override.

## Environment Files

- `frontend/.env.test` – loaded by `playwright.config.ts` through `dotenv` when it exists. It is gitignored and the repository ships none; create it for local Playwright overrides such as log streaming (see [CI & Execution → Environment Overrides](./testing/ci_and_execution.md#environment-overrides)).
- `frontend/.env.example` – names `BACKEND_URL` with its default. `vite.config.ts` reads `BACKEND_URL` and `VITE_TEST_MODE` from the process environment, and Vite does not load `.env` files into it, so a `frontend/.env` changes neither. Set them on the command instead: `cexec modern-app env BACKEND_URL=http://localhost:<port> pnpm dev`.
- `backend/.env`, `backend/.env.test` – the backend's settings, generated by `kc project setup backend`. Each worker's backend reads `.env`, with `.env.test` over it (`backend/scripts/testing-server.sh`).

## Vite Proxy & Per-Worker Managed Services

- **API proxy**: The dev server forwards `/api/**` to `BACKEND_URL` with `changeOrigin`. It sends `X-Forwarded-Host` and `X-Forwarded-Proto` unless a proxy in front already set them, so the backend builds absolute URLs, such as the OIDC redirect URIs, from the origin the browser used.
- **SSE proxy**: `/api/sse/**` goes to `BACKEND_URL` too, which serves the SSE stream. The rule flushes an event stream's response head at once, so `EventSource.onopen` fires on connect rather than on the first heartbeat. It is listed before `/api`, so the more specific prefix wins.
- **App proxies**: `loadAppProxies()` in `vite-proxy-extensions.ts` merges app-owned rules ahead of both; IoTSupport adds none.
- `pnpm preview` uses the same rules.
- Only `/api` is proxied: the backend's `/health/*` and `/metrics` stay off the frontend's origin, and the dev server answers those paths with `index.html`.
- At startup the dev and preview servers probe `BACKEND_URL`'s `/health/readyz` once and log a warning when it does not answer OK; they start regardless.
- **Per-worker services**: Each Playwright worker starts its own backend, then its own frontend with `BACKEND_URL` set to that backend, and waits for both to report ready (backend `GET /health/readyz`, frontend `/`). See [CI & Execution → Per-Worker Managed Services](./testing/ci_and_execution.md#per-worker-managed-services) for the startup sequence, timeouts and health checks.

Global setup refuses `PLAYWRIGHT_MANAGED_SERVICES=false`: the suite always runs its own services.

## Test Mode

When `VITE_TEST_MODE=true`:
- `isTestMode()` is true: `main.tsx` installs the console policy and the error instrumentation, and the emitters in `src/lib/test/` send test-event payloads to the Playwright binding `window.__playwright_emitTestEvent`, which the Playwright fixtures register.
- Vite aliases `esptool-js` to `tests/support/mocks/esptool-mock.ts`, so Flash device and Provision device run against the suite's fake USB device.
- The dev server stops watching files, so an edit does not reload the page.

The console policy only records `console.error` calls; failing a test on an unexpected one is the Playwright `page` fixture's job.

A build without `VITE_TEST_MODE=true` defines it as `'false'`, so every `isTestMode()` guard is false in production; `pnpm build` runs `verify:build`, which reports test markers left in the bundle. Keep new instrumentation behind `isTestMode()` checks. `VITE_TEST_MODE=true pnpm build` makes a production build with the Playwright bridges in it, for [preview mode](./testing/ci_and_execution.md#preview-mode). See [Test Instrumentation](./architecture/test_instrumentation.md) for details.

## Backend Collaboration

The Playwright suite relies on the backend for:
- `backend/scripts/testing-server.sh --host <host> --port <port> --database-url <url>` – starts a worker's backend with `FLASK_ENV=testing`.
- `GET /health/readyz` – the readiness probe each worker polls until it answers HTTP 200.
- `uv run cli load-test-data --yes-i-am-sure` – loads the backend's test data into the run's seed database in global setup.
- The `/api/testing/*` endpoints, which answer only under `FLASK_ENV=testing` on a `STAGE` other than `prd`. [Testing Overview → Backend Responsibilities](./testing/index.md#backend-responsibilities) lists the ones the suite drives.

Each worker's backend output is collected from its process and attached to every test result as `backend.log`. Coordinate with backend contributors to keep these entry points aligned with the suite.
